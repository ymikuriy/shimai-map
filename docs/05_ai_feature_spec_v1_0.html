05_AI機能仕様書

AI機能仕様書 v1.0

家の中のモノを探すアプリにおけるAI利用範囲、UI上の扱い、データ契約、評価方法、実装検討ポイントをまとめる。AIは「ユーザー入力を増やさず、検索しやすくする補助機能」として扱う。

版: Draft v0.1 対象: カテゴリ候補 / 検索補助語 / 検索補助 方針: AIは補助。自動確定しない 作成日: 2026-05-02

0. AI開発エージェントへの検討依頼

本仕様書はAI利用方針のv1.0案。
カテゴリ候補生成・検索補助語生成をMVP候補とするが、開発時には、実現可否、APIコスト、レスポンス速度、個人情報送信範囲、ルールベース代替案を評価し、最終案を提案すること。
項目AI開発エージェントに検討させる内容
カテゴリ候補生成MVP実装可否、既存カテゴリ優先ロジック、UIレスポンス、コスト。
検索補助語生成保存時生成、再生成タイミング、内部保持方式、検索精度への効果。
検索時AIフォールバックPhase2候補。速度・コスト・結果ブレ・ユーザー説明の観点で評価。
対象外AIによる所在推定、画像認識による自動登録、検索時の毎回AI API呼び出しはMVPでは原則対象外。

1. 位置づけ

結論：本アプリでは、AIを「登録を楽にする」「検索に引っかかりやすくする」ために使う。部屋・収納・所在などの確定情報はAIに決めさせない。
分類扱い理由
所在情報AI対象外部屋・収納・エリアはユーザーが確定する。検索結果の信頼性に直結するため。
カテゴリ候補AI対象登録時の選択負担を下げる。ユーザーが採用/削除するため誤りを制御しやすい。
検索補助語AI対象「カッパ」「レインウェア」「雨具」など呼び方の違いを内部的に吸収できる。
検索時AIフェーズ2候補毎回AI APIを呼ぶと速度・コスト・ブレの課題がある。MVPは登録/保存時AIを基本とする。

2. 世の中の既存資料との関係

AI機能向けのPRDテンプレート、Human-AI設計ガイド、AIリスク管理フレームワーク、モデルカードのような資料は存在する。ただし、本アプリではそのまま使うと重いため、実装検討に必要な項目だけを軽量化して使う。

AI PRD

AI機能は従来PRDより、性能閾値・失敗モード・データ依存・継続監視が重要。

Human-AI UX

AIがどこでユーザーを助け、どこでユーザーに確認させるかを設計する。

Risk Management

信頼性、プライバシー、誤生成、運用監視を仕様段階で整理する。

Model/System Card

モデルやAIシステムの用途、限界、評価、リスクを記録する考え方。

この資料の役割：外部の汎用テンプレートではなく、このアプリのAI機能を実装判断できる粒度に落とした「AI機能仕様書」とする。

3. AI利用範囲

AI-02検索補助語生成アイテム保存時/検索影響項目の更新時表示しない。内部検索用高

MVP推奨：AI-01、AI-02までを必須対象にする。AI-03、AI-04は実現可否・コスト確認後に採用判断する。

入力

ユーザー確認

5.2 保存時検索インデックス生成

3
並び順に従って表示
AI APIは原則呼ばない
4
0件時のみ候補提示はフェーズ2で検討

6. 入出力・データ

項目保存先ユーザー表示用途
category_idsitems / item_categories表示する検索・絞り込み・一覧表示
ai_search_keywordsitems または item_search_index表示しない表記ゆれ、同義語、言い換え検索
ai_keyword_versionitems表示しない生成ロジック変更時の再生成判定
ai_generated_atitems表示しない再生成・監査・デバッグ
ai_candidate_log必要ならログ表示しない品質改善。個人情報を含めない設計にする
データ最小化：AI APIには、原則としてアイテム名・既存カテゴリ名・選択済みカテゴリだけを送る。部屋名、収納名、人物ラベル、メモは必要性がない限り送らない。

7. プロンプト/API契約

7.1 カテゴリ候補生成API

POST /ai/category-candidates request: { "item_name": "レインコート", "existing_categories": ["衣類", "書類", "雨具", "薬", "工具", "季節用品"], "selected_categories": ["雨具"], "max_existing_candidates": 3, "max_new_candidates": 1 } response: { "existing_candidates": [ {"category_name": "衣類", "reason": "身に着ける雨具", "confidence": 0.86}, {"category_name": "季節用品", "reason": "雨季に利用されやすい", "confidence": 0.72} ], "new_category_candidates": [ {"category_name": "アウトドア用品", "reason": "屋外活動でも使うため", "confidence": 0.55} ] }

7.2 検索補助語生成API

POST /ai/search-keywords request: { "item_name": "レインコート", "categories": ["雨具", "衣類"], "max_keywords": 12 } response: { "keywords": ["カッパ", "合羽", "レインウェア", "雨具", "梅雨", "雨の日", "外出", "通学"] }
API契約ルール：AI出力は必ずJSONで受け取り、スキーマ検証、重複除去、文字数制限、禁止文字除去を行う。検証に失敗した場合はAI候補なしとして通常登録を継続する。

8. 評価・成功条件

評価対象確認方法合格目安
カテゴリ候補の妥当性代表アイテム50〜100件で手動評価上位3候補のうち1つ以上が妥当: 80%以上
不要カテゴリの少なさ明らかに不適切なカテゴリ率10%未満
検索補助語の有効性別名検索で期待アイテムがヒットするか主要ケースで80%以上
レスポンス候補ボタン押下から表示まで体感2秒以内を目標。超える場合はローディング表示
コスト1登録あたりのAI呼び出し回数MVPは最大2回。候補生成1回 + 保存時補助語1回

9. リスク・制約

誤分類

カテゴリ候補が誤る可能性がある。対策として、AIは自動保存せず、ユーザーが選んだものだけ保存する。

検索のブレ

検索時に毎回AIを呼ぶと結果がブレる。MVPでは保存済み検索補助語を使い、検索は内部処理を基本とする。

プライバシー

パスポート、保険証書、薬などセンシティブなアイテム名があり得る。AI API送信項目を最小化し、メモや所在詳細は送らない。

障害時

AI APIが失敗しても、アイテム登録・検索は継続できる。AI候補なし、または後で再生成する。

10. 実装タスク

優先タスク内容
1カテゴリマスタ整備初期カテゴリ、ユーザー追加カテゴリ、同義語管理方針を定義
2AIカテゴリ候補APII01の候補ボタンから呼び出す。既存カテゴリ優先
3AI検索補助語生成保存時に実行し、内部検索インデックスへ保存
4検索インデックス拡張アイテム名、カテゴリ、人物ラベル、AI補助語を検索対象にする
5評価データ作成家庭内アイテム50〜100件の評価セットを作る
6ログ/監視失敗率、採用率、候補表示時間、検索0件率を記録

11. 仕様ID

ID仕様
AI-001AIは補助機能とし、所在情報を自動確定しない。
AI-002カテゴリ候補はユーザー操作で表示し、自動保存しない。
AI-003カテゴリ候補は既存カテゴリを優先し、該当が薄い場合のみ新規カテゴリ候補を出す。
AI-004検索補助語は保存時または検索影響項目変更時に生成し、ユーザーには表示しない。
AI-005通常検索ではAI APIを原則呼び出さず、保存済み検索インデックスで検索する。
AI-006AI API失敗時も登録・検索の基本操作は継続可能とする。
AI-007AI APIに送るデータは必要最小限とし、部屋名・収納名・人物ラベル・メモは原則送らない。
AI-008AI出力はJSONスキーマで検証し、検証失敗時は候補なしとして扱う。
AI-009AI機能の品質は候補採用率、検索0件率、別名検索ヒット率、失敗率で評価する。
