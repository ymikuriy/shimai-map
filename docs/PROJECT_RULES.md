# Shimai-Map プロジェクト開発ルール (PROJECT_RULES)

本ドキュメントは、「Shimai-Map」プロジェクトにおけるAIエンジニア（エージェント）および開発者が**常に厳守すべき**ルールと方針を定義したものです。

## 1. 基本方針と技術スタック
アプリの主目的は「家の中のモノを検索して所在確認すること」です。MVPは「1ユーザー=1家」とし、リアルタイムなUI操作感とオフライン耐性を重視します。

- **基盤技術**: React + Vite, TypeScript, TailwindCSS
- **インフラ/BaaS**: Firebase (Auth, Firestore, Storage)
- **主要ライブラリ**: 
  - **react-rnd**: 部屋・収納レイアウトの直感的なドラッグ＆リサイズ操作。
  - **Zustand**: UIの開閉状態、ドラッグ中の状態、作成中の一時データ（Draft State）管理。
  - **React Context**: Firestoreデータのアプリ全体への提供（`AppDataContext`）。
  - **shadcn/ui**: 共通UIコンポーネントベース（低コストかつ高品質なUIの実現）。

## 2. アーキテクチャとディレクトリ構造
FSD (Feature-Sliced Design) をベースに、機能ごとの凝集度を高めます。

- **`src/features/`**: 機能単位（`search`, `items`, `rooms` 等）。機能内で完結するコンポーネントやロジックはここに閉じる。
- **`src/components/`**: 複数機能で共有する汎用UI（Button, Dialog 等）。
- **`src/contexts/`**: グローバルデータプロバイダ。
- **`src/hooks/`**: 汎用フック。
- **`src/services/`**: Firebase通信やAI API呼び出し処理。
- **`src/types/`**: アプリ全体の型定義。

**【依存ルール】**
`features/A` が `features/B` の内部モジュールを直接 import することを**固く禁じます**。必ず共通層（`components`, `contexts` 等）を経由してください。

## 3. コード規約と品質基準
- **Airbnb TypeScript Style Guide** に準拠します。
- **`any`型の禁止**: ESLint `no-explicit-any` を厳守し、不明な型は `unknown` やジェネリクスを使用します。
- **マジックナンバーの排除**: UI上の固定ピクセルや設定値は、必ず定数として定義します。
- **関数のサイズ**: 1関数は原則50〜100行以内に抑え、複雑なロジックはカスタムフックに分離します。
- **命名規則**: 
  - コンポーネント・TSXファイル: `PascalCase`
  - 関数・変数・TSファイル: `camelCase`
  - 定数: `UPPER_SNAKE_CASE`

## 4. UI/UXデザインと操作のルール
アプリの売りである「レイアウト編集の操作感」と「検索体験」を最優先します。

- **コンポーネント適用**: shadcn/ui等の標準コンポーネントを活用して低コストで「やっている感（高品質な操作感）」を演出します。
  - ステップ式入力（I02）: 独自アニメーションではなく、アコーディオンやモーダル等の標準UIを工夫して実装します。
  - タグ操作（I03）: 画面遷移させず、PopoverやCommandを用いたインライン操作を採用します。
- **レイアウト編集（R02/R03）**: 
  - 詳細移動用の矢印ボタン等は当面不要とし、**ドラッグ＆ドロップによる直感的な移動とサイズ変更（react-rnd）**に特化します。
  - 部屋の形状はプリセット選択ではなく、**「部屋レイアウトの枠自体もドラッグでリサイズ可能」**とします。
- **状態（State）の引継ぎと保護**:
  - I01（アイテム登録）で入力中のデータは、Zustand等で保持し、別画面に遷移しても消えないようにします。
  - 戻り先の動的変更: 「どこから呼ばれたか（`returnUrl`）」をパラメータやZustandで保持し、保存完了後の遷移を制御します。
  - **破壊的変更の警告**: 編集時に「部屋」を変更した場合など、既存の収納・エリア情報がリセットされる操作には、必ず**確認ダイアログ**を表示します。

## 5. AI関連ルールとコスト最適化
- **AIの役割**: AIはユーザー入力を「補助」するものであり、所在データなどを自動確定させません。
- **検索補助語の生成**: アイテムの**保存時**にのみAIを利用して「検索補助語（同義語や表記ゆれなど）」を裏側で生成・DB保存します。毎回の検索時にAPIを叩くことは禁止し、コストとレスポンス速度を最適化します。
- **カテゴリ候補**: AIカテゴリ候補はユーザーの要求時のみ表示し、選択されたものだけを保存します。
- **Firestore通信**: キャッシュを適切に利用し、無駄なリード（読み取り）回数を減らすよう設計します。

## 6. AIエージェント（私）の検証ルール
AIエージェントはコードを書く際、必ず以下の自己検証を行います。
- `any` が含まれていないか。
- `features` 間の不正な依存がないか。
- 破壊的変更前にダイアログ等の保護が入っているか。
- 静的解析（ESLint / TypeScript）を実行し、エラーがない状態で完了報告を行うこと。
